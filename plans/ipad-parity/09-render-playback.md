# 09 · Render & Playback

> **Status:** Render & Playback is one of
> the most mature parity themes. Both apps share the same `src-core/render/`
> engine, `RenderCache`, and `OutputManager`, so the *render logic* and
> *network output* are identical — the iPad genuinely streams DDP/E1.31/
> ArtNet to controllers (`OutputManager::StartOutput`), runs the same
> multi-threaded `RenderAll`, and persists `.fseq` to disk on save. The
> surviving gaps are almost entirely **UI surface**: the iPad has no
> discrete volume-preset menu (it uses a toolbar slider instead), no
> separate Pause toolbar button (it folds pause into the play/pause
> toggle), and no "Log Render State" diagnostic. iPad now has a
> dedicated Replay-Section toolbar button + Playback-menu entry. Conversely the iPad has **richer touch idioms** —
> ruler drag-to-scrub with audible 50 ms bursts, long-press loop-region
> banding, and double-tap-a-timing-mark-to-loop — that have only rough
> keybinding analogues on desktop. The continuous transport
> position slider for coarse seeking — formerly the single most notable
> *iPad-missing* item — now ships on iPad as a transport-strip `Slider`
> (audible 50 ms scrub bursts during drag, final seek on release)
> alongside the Metal-ruler tap/scrub. Loop-region and "render just this region" exist
> on **both** platforms (desktop: `PLAY_LOOP` keybind + Replay-Section +
> Waveform "Render Selected Region"; iPad: B32/B33/B44 loop region).

> **Note (2026-07):** the Linux/Windows desktop gained a Vulkan GPU compute
> backend (`src-core/effects/vulkan/`, `HAVE_VULKAN`) mirroring the Metal
> backend's `GPURenderUtils` implementation (blur/rotozoom/transitions/layer
> blending). Apple platforms (desktop + iPad) keep the Metal backend — the
> Vulkan sources compile to nothing there, so no iPad action is needed.
>
> **Update (2026-07-24):** fixed a Vulkan-only render-nondeterminism where
> GPU-built transition masks (Wipe, etc.) were copied on the CPU from the
> still-in-flight GPU mask buffer before its writing dispatch was fenced,
> producing nondeterministic masked-transition output. The fix binds the GPU
> mask buffer directly to the blend, which is exactly what the Metal backend
> already does (`MetalComputeUtilities.mm` blend loop) — so this brings Vulkan
> to parity with the already-correct Metal path; **no iPad change needed** and
> the Metal render path was never affected.

Measured on Windows/AMD: `GreatestShow` 133s → 117s, `IntoTheUnknown` 241s → 107s, output byte-identical to software decode. 2026-07-30: the decode-size machinery above was sizing itself off a bogus "native" size. `SharedDecoder::open` took `CGSizeApplyAffineTransform(naturalSize, preferredTransform)` as the source dimensions, which picks up the transform's SCALE, not just its 90-degree rotation — a file whose display matrix encodes its pixel aspect as a scale (seen in the wild as scale(853, -9217) on a 640x480 clip) reported native 545920x4424160, so the decode target computed as a fraction of it came out at 1200x9724, ABOVE the source. Every frame in the shared 64-entry cache and in each consumer's 16-entry private cache was then 46MB instead of 1.2MB. Native is now the coded size with only the transform's axis swap applied, plus an explicit clamp so the decode target can never exceed the source whatever the metadata claims (`macOS/src-apple-core/media/AVFoundationVideoBridge.mm`, both `SharedDecoder::open` and `AVPlayerDecoder::open`). Apple-only file, shared by desktop and iPad — **auto-applied to iPad**, no UI or bridge surface. Measured on one user-supplied video-heavy sequence: peak RSS 46.6GB → 5.4GB and render wall 195s → 7s (the upscaled decode was also most of the render time). **The iPad gains proportionally more** — it is the memory-constrained client and would have been killed outright by the old sizing. Not a behaviour change so much as a restoration: before the decode-scaling entry above (2026-07-24) every file decoded at native, so a file with this metadata is back to the output it had then, while files with sane metadata keep the intended downscale. The one genuine change is that for anamorphic sources "Maintain Aspect Ratio" now follows the coded aspect rather than the display aspect. 2026-07-31: decode-scaling was still being defeated whenever ONE effect rendered a file large: the target is (largest render size x AA headroom), so a whole-house group at 1335x217 x3 exceeded a 1920x1080 source, clamped to native, and every consumer of that file — most of them tiny — paid 8MB/frame caches (33MB for a 4K source). In that clamped-to-native case only, the target now falls back to the smallest scale that still covers the largest render size while keeping the media engine's own reduction within 2x (`XL_VIDEO_MAX_VT_FACTOR`); files whose headroom already fits under native are untouched, and the force-native sentinel still wins. Separately, both frame caches (the shared per-file one, 64 entries, and each consumer's private 16) are now bounded in BYTES measured from the decoded buffer, not just in frame count — the pre-existing byte budget could only ever RAISE capacity (`std::max(kCacheCapacity, ...)`) so it never bound a 4K file, and it charged native dimensions rather than the decoded ones. Cache floors must stay above `kReadAheadFrames`: a private cache smaller than one read-ahead batch round-robins over its own entries, never serves a hit, and sends every frame through the shared decoder mutex (measured: 88s render -> >18min). Apple-only file shared by desktop and iPad — **auto-applied to iPad**, no UI or bridge surface. Measured on one video-heavy sequence (164 video effects, nine files, one 4K): peak footprint 22.4GB -> 8.4GB, render CPU -35% (smaller frames cost less to scale and convert, so this is not a memory/speed trade). **The iPad gains proportionally more** as the memory-constrained client, and its headroom default of 2 means the fallback engages there for any file whose largest consumer is over half the source size. 2026-07-31: the same shared bridge was also rendering video-heavy sequences NON-DETERMINISTICALLY — two identical runs of one sequence differed on 64,623 of 135,844 channels (maxD 227); with the video effects removed the same sequence was byte-identical. Cause: chain-origin verification only ever sets isIDR inside its H.264/HEVC branch, so an all-intra file (MJPEG, ProRes) kept exactly ONE origin ("1 of 900 container syncs are true IDRs") and computeOrigin anchored every chain at decode index 0 — each reposition re-decoded the prefix from the start of the file. On 1920x1080 MJPEG that held decode chains long enough that other consumers hit the 30s wait-for-a-chain timeout (397 of them in one render, all on the two MJPEG files), and that timeout set `outAtEnd`, which the Loop/Manual-and-Loop duration treatments consult — so a transient stall wrapped a looping effect early and every later frame of it differed, with which consumer stalled decided by thread scheduling. Two fixes: run NAL verification only for the codecs that actually have the open-GOP hazard (everything else is all-intra, where a container sync IS a canonical entry point), and stop reporting a resource stall as end-of-stream. The sequence is now byte-identical run to run (3 runs gated), zero timeouts, and wall time fell 94s -> 34s from these two alone — the prefix re-decoding was also most of the render. Apple-only file shared by desktop and iPad — **auto-applied to iPad**, no UI or bridge surface. **This mattered more on iPad**, which has fewer cores: the same chain contention that produced the stalls is proportionally worse there. Note for future byte-gating: a sequence using an all-intra video could not be byte-gated at all before this, because its own run-to-run noise floor exceeded most real diffs. |

## Infeasible / restricted on iPad

- **Output to Lights — USB / serial / DMX dongles.** The iPad path
  (`OutputManager::StartOutput`) works for **network** protocols only
  (DDP, E1.31/sACN, ArtNet, FPP/Player). Raw USB-serial DMX/Renard
  outputs need a USB UART the iPad can't drive; those output types are
  **infeasible** on iPad. Network output is full parity.
- **Output requires controllers pre-configured.** `toggleOutput` errors
  with "Set up controllers in desktop xLights and copy the show folder"
  when `outputCount() == 0`. Adding/editing **closed-firmware** controller
  definitions on iPad is **restricted** (IAP-gated, P3) per the firmware
  rule; open-source firmware (FPP/WLED/ESPixelStick/DDP/generic) config is
  in scope but lives under the Controllers theme, not here.
- **Log Render State** is feasible but low value (see above) — left
  desktop-only by choice, not a platform limit. (Render bell has since
  landed on iPad — see the scorecard row.)
