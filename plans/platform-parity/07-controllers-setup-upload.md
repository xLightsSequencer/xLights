## Vendor upload matrix

Every vendor handler is dispatched by the shared factory `BaseController::CreateBaseController`
(`src-core/controllers/BaseController.cpp:50-107`), called from desktop
`TabSetup.cpp:1591` (input) / `:1664` (output) and from iPad `XLSequenceDocument.mm:16942`.

**The single decisive fact for this table:** the iPad bridge's `runUpload:input:`
(`XLSequenceDocument.mm:16892-16980`) is vendor-agnostic and gated only on
`caps->SupportsUpload()` / `SupportsInputOnlyUpload()` — exactly like desktop. But **both** iPad UI
entry points that can reach it are wrapped in `if openSourceFirmware` — the row context menu
(`LayoutEditorView.swift:2404-2414`) and the detail-pane button bar (`:12407-12420`). Only
`resources/controllers/fpp.xcontroller` and `resources/controllers/wled.xcontroller` contain an
`<OpenSourceFirmware>` node (verified: `grep -rl OpenSourceFirmware resources/controllers/` returns
exactly those two of 25 vendor files; the cap is read at `ControllerCaps.cpp:416-419`). So on iPad,
upload is reachable for FPP- and WLED-family fixtures only, and every other vendor's working upload
code is dark.

## Notes

**Headline.** The iPad's controller story is far stronger than a read-only viewer: it has genuine
CRUD (`XLSequenceDocument.mm:16581-16615`), the same six discovery scanners, per-controller and bulk
upload through the same `BaseController` factory, a full property pane, and a three-phase FPP Connect.
Of 94 feature rows: **40 ✅, 29 🟡, 23 ❌, 2 🚫**. Of 21 output types: 10 ✅ / 8 🟡 / 2 ❌ for
configuration, and 7 ✅ / 1 🟡 / 10 🚫 for live output. Of 14 vendor handlers: 3 ✅, 1 🟡, 10 ❌.
The gaps cluster into four groups, and one of them is worth far more than the rest.

**1. The `openSourceFirmware` gate: deliberate policy; one deferred data gap, one wrong predicate.**
Both iPad entry points to Upload and Visualize are wrapped in `if openSourceFirmware`
(`LayoutEditorView.swift:2403`, `:12407`). The gate itself is deliberate: on iPad, controller
config/upload is in scope for **open-source-firmware controllers only**; the closed-firmware
vendors (Falcon, HinksPix, SanDevices, AlphaPix, J1Sys, Minleon, Experience, PowerDMX, ILightThat,
vendor-FW Pixlite) are deliberately out of scope at present — so the ten ❌ vendor-matrix rows are
**policy-restricted, not parity bugs**. Within the policy:
(a) *Kulp/K-boards are already in scope* — their variants declare `Base="FPP:FPPStringCape"`
(`resources/controllers/kulp.xcontroller`), and caps loading merges base-chain nodes
(`ControllerCaps.cpp:46-59`), so they inherit `<OpenSourceFirmware/>` from `FPP:BaseFPPSettings`
(`fpp.xcontroller:30-31`, chain at `:54`) at runtime. (An earlier draft claimed kulp was blocked;
that came from grepping the file for the literal node name, which misses inherited caps.)
(b) *ESPixelStick is a real gap* — open firmware, but no FPP base chain and no
`<OpenSourceFirmware/>` node in `espixelstick.xcontroller`, so it is blocked despite being
intended in-scope. **Known and deferred by decision (2026-08-01) — fix later.**
(c) *Visualize is gated on the wrong predicate.* The wiring view writes nothing to firmware;
desktop gates it on `Controller::CanVisualise()` (`Controller.cpp:545-552`,
`ControllerListPanel.cpp:1341`), so a Falcon/HinksPix user loses a read-only view for no policy
reason (row 29).
The bridge already dispatches every vendor handler correctly through the caps gate
(`XLSequenceDocument.mm:16908-16924`).

**2. Per-protocol output properties stop at E1.31/ArtNet/KiNET.** `XLSequenceDocument.mm:15947`
builds the Output section only for those three protocols, so DDP, ZCPP, Twinkly, OPC, xxx-Ethernet,
LOR-Optimised and xxx-Serial can be *selected* but not *configured* — 17 distinct desktop property
rows are unreachable (verified absent by grep for each label). Structurally this wants the same
adapter-per-protocol shape desktop uses in `OutputPropertyAdapters.cpp`; the descriptor-dictionary
format the iPad already emits (`CtrlIntProp` / `CtrlBoolProp` / `CtrlStringProp` /`CtrlEnumProp`,
`:15772-15825`) is expressive enough that each protocol is a self-contained addition. DDP first — it
is the most-used of the seven and needs only three rows.

**3. FPP Connect's missing FSEQ Type picker is a correctness bug, not a convenience gap.** The
bridge hardcodes `fseqType = 2` (V2 Sparse/zstd) at `XLSequenceDocument.mm:18640`. Devices that
require V1 or V2-uncompressed — which desktop offers per-instance and persists per-UUID
(`FPPConnectDialog.cpp:657-675`, `:1721-1726`) — will receive files they cannot play, with no
indication why. The device capability is already known at that point in the same function
(`:18668` already branches on `FPP_TYPE::ESPIXELSTICK`), so this is a small, well-scoped fix.

**4. Three silent-correctness gaps worth fixing before any UI work.** None is visible to the user
until it has already caused harm. (a) `DidConvert` is never consulted on iPad — grep returns zero
hits across `src-iPad/` — so a legacy `xlights_networks.xml` is re-migrated on every open and the
migration is never persisted unless an unrelated edit dirties the show (desktop handles this at
`TabSetup.cpp:456-461`). (b) There is no iPad equivalent of `NetworkChangesAllowed()`
(`ControllerListPanel.cpp:505-507`): `isOutputting` is bridged at `XLSequenceDocument.mm:12241` but
`LayoutEditorView.swift` never reads it, so controllers can be deleted or reprotocolled while
frames are being pushed to real hardware. (c) Smart-remote **type** is written to a single model on
iPad (`XLSequenceDocument.mm:5281-5287`) even on a controller whose caps declare
`AllSmartRemoteTypesPerPortMustBeSame` — desktop propagates across the whole four-port block
(`ModelPropertyAdapter.cpp:1343-1362`). Row 89; it hides inside the otherwise-✅ row 37.

**Suggested porting order within this theme:** (1) re-gate Visualize on a bridged `canVisualise`
instead of the firmware policy (the espixelstick caps node is a known, deliberately deferred fix;
kulp needs nothing — it inherits);
(2) the two silent-correctness gaps above; (3) FSEQ Type picker; (4) per-protocol output properties,
DDP first; (5) discovery seeding + auth delegate (rows 51-52 — the auth prompt already exists in
`FPPAuthPrompt.swift` and just needs registering on the discovery path); (6) the visualizer's bulk
port operations (rows 34-36, 38-39); (7) list-surface depth — port/model tree and the missing
columns (rows 1-3, 88). Row 89 (smart-remote type propagation) belongs with step (2) — it is a
correctness fix, not a UI addition.

**Bridge observations.** The iPad's controller work is unusually well-factored: the property pane is
a data-driven descriptor list (`controllerPropertiesForName:`, `XLSequenceDocument.mm:15826-16105+`)
rather than hand-built views, so new property rows are additive on the ObjC++ side with no SwiftUI
change. Protocol and baud lists are pulled live from core
(`SerialOutput::GetPossibleBaudRates()` `:15694`, `GetPossibleSerialPorts()` `:15705`) rather than
duplicated, so they cannot drift. Several in-code comments explicitly cite the desktop line they
mirror, which made this audit unusually verifiable. Two comments are stale and worth correcting
while in the area: `LayoutEditorView.swift:47-49` says "iPad doesn't yet have a controller editor"
(it does, ~1300 lines below in the same file), and `SequencerViewModel.swift:3241` tells the user to
"Set up controllers in desktop xLights and copy the show folder to the iPad" when the iPad can now
do exactly that itself.
