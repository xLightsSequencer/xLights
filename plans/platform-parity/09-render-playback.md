## Notes

- **The single biggest structural gap is the render progress sink.** `iPadRenderContext::RenderAll` passes `nullptr` for `IRenderProgressSink` (`src-iPad/Bridge/iPadRenderContext.cpp:2014-2018`), so rows 14 and 15 both fall out of one omission. The core already carries everything needed — `IRenderJobStatus::SetProgressCallback` / `GetStatusForUser` — so a Swift-facing sink that publishes an array of `(name, percent, status)` would close both rows at once and is the highest-value single change in this theme. Note that the stall watchdog (row 16) is *not* part of this gap: it already runs on iPad because `xLightsShowContext::IsRenderDone` drives `CheckForStalledRender` and the iPad's poll calls it.
- **Render dependency tracking is genuinely missing, not just unsurfaced** (row 7). Desktop polls `SequenceElements::GetElementsToRender` on every output-timer tick; the iPad has no equivalent tick and never calls `RenderEngine::RenderDirtyModels`. Effects that depend on a timing track or on another model's output will silently go stale on iPad until the user hits Render All. This is a correctness gap, not a UI gap, and should rank above the cosmetic items.
- **Two output-lifecycle bugs worth fixing cheaply.** Row 88: `stop()` never blanks the outputs, so lights hold the last rendered frame after Stop — desktop calls `_outputManager.AllOff()` (`src-ui-wx/sequencer/tabSequencer.cpp:2094-2096`) and the same call is already available through `iPadRenderContext::GetOutputManager()`. Row 113: `GPURenderUtils::prioritizeGraphics` is never toggled on iPad, so a background render competes with preview drawing during playback.
- **The two "Render on Save" toggles do different things** (row 27). Desktop forces a full re-render then writes the fseq; iPad only writes the fseq from whatever `SequenceData` already holds. Given the iPad renders continuously that is usually equivalent, but after a memory-pressure abort it is not — the code already detects that case and skips the write (`src-iPad/App/SequencerViewModel.swift:1779-1790`). Renaming the iPad toggle, or making it kick a render first, would remove a real footgun.
- **Batch Render diverges in both directions.** The iPad is ahead on ergonomics (out-of-date filter, sort, persisted selection, memory-pressure retry — rows 49, 50, 51, 54) and behind on scoping and control (folder filter, Select Highlighted, Select From FPP Playlist, Force High Definition — rows 43, 45, 46, 47). Force High Definition is the one that changes output rather than convenience, so port it first: it is a single boolean around the existing `render.lowDefinition` read.
- **FSEQ writing is nearly at parity through the shared `FSEQFileIO`.** Only the version selector (row 30) and the effect-sequence flavor (row 34) are unreachable from iPad, and both are single-field additions to the `WriteOptions` already being filled in `iPadRenderContext::WriteFseq`. The iPad's independent compression picker and zstd level (rows 31, 32) are arguably better than the desktop's version-coupled choice and are candidates for reverse porting.
- **Preview parity is close; the transport strip is the visible hole.** Rows 95–98 all describe the same absence: the iPad preview pane has no play controls and no auto-show behavior, so the House Preview is a passive surface. Since the view model already exposes every transport action, adding an optional overlay strip is a view-layer change with no bridge work.
- **Suggested porting order within this theme:** (1) render dependency polling — row 7; (2) progress sink with per-job detail — rows 14–15; (3) `AllOff` on stop plus `prioritizeGraphics` during playback — rows 88, 113; (4) Force High Definition in Batch Render — row 47; (5) preview transport overlay and auto-show — rows 95–98; (6) FSEQ version selector — row 30; (7) ISEQ / data-layer rendering — row 8, which needs bridge and UI work for data layers that the iPad does not model at all yet.
- **Genuinely out of reach:** the four CLI modes (rows 35–39) have no iOS analogue; serial/DMX output (row 90) is stubbed at the `SerialPort` level for `TARGET_OS_IPHONE`; and Keep-on-Top and Suppress-Dock (rows 104, 105) describe window managers that iPadOS does not expose to apps.
