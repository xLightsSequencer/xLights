## Notes

- **The theme is in better shape than its size suggests.** Of 91 rows, the large blocks — the whole light test, the whole Check Sequence engine, the whole Help link set, the command palette, the diagnostic upload endpoint — are at or near parity, and three of them are *shared core*, not parallel implementations. `xltest::TestPatternEngine` (`src-core/outputs/TestPatternEngine.h`) and `SequenceChecker` / `CheckSequenceReport` (`src-core/diagnostics/`) are the model to copy: one implementation, two thin UIs, and a test preset saved on one platform loads on the other.

- **The real gaps cluster in three places.** (1) Light-test *targeting*: the engine is shared but the iPad can only aim it at models and controller ports — no Outputs tree, no Model Groups tree, no search filter (rows 8, 9, 11). (2) Crash-time capture: the iPad has no in-process fatal handler, so a crash report has no backtrace until MetricKit delivers one a day later (rows 72, 73). (3) Report *output*: Check Sequence produces no shareable artifact on iPad (row 21) and the log package omits the models/effects exports and the settings dump (rows 42, 77).

- **Two rows are quiet correctness bugs, not missing features.** Row 57: `TipOfDaySheet.showNextTip()` parses each tip's `level` and then ignores it, picking uniformly at random with no visited-set — the file's own doc comment claims it "honors the min level filter", which it does not. Row 66: the iPad release-notes URL omits desktop's strip-the-patch-version fallback, so a patch release without a tagged `README.txt` opens a 404. Both are a few lines to fix and neither needs new bridge surface.

- **Row 69 deserves a decision, not just a status.** The macOS App Store build deliberately routes Donate through StoreKit; the iPad — also Store-distributed — opens a PayPal URL. Whatever the right answer is, the two Apple platforms currently disagree with each other about the same question.

- **Bridge surface needed for the remaining ports, smallest first.** `LogRenderStatus()` (row 46) needs one bridge method over an engine call the iPad already links. Cleanup's rgbeffects half (row 28) needs the existing `cleanupExternalMedia` sweep extended over `AllModels` / `AllObjects` / the preview background — the desktop half is 20 lines (`src-ui-wx/xLightsMain.cpp:6525-6546`). Light-test Outputs and Model Groups trees (rows 8, 9) need two more enumerator methods alongside `modelItems` in `src-iPad/Bridge/XLLightTest.mm` and reuse the channel-range selection API that already exists. Check Sequence export (row 21) needs only a call to the `GenerateHTML` the core report already has, plus a share sheet.

- **Suggested porting order within this theme:** (1) the two bug-fix rows, 57 and 66; (2) row 46, Log Render State; (3) row 28, cleanup's model/object half — it is the one gap here that silently leaves a show non-portable; (4) rows 8 and 9, the missing test-target trees, which is the field-usability gap the light test exists for; (5) row 21, Check Sequence export; (6) rows 42 and 77, log-package completeness. Rows 72/73 (crash-time backtrace) are a larger piece of work and arguably better answered by leaning harder on MetricKit than by adding a signal handler to an App Store binary.

- **Rows carried by other themes.** 30 (theme 08), 32 (09), 33/34/35/39 (07), 36/50 (12), 37/38 (08), 48/49 (06), 51 (03), 52 (08). They are listed here because they are Tools-menu entries and this scorecard walks that menu exhaustively; their detailed analysis belongs to the owning theme.

- **Rows 86-91 came from a cross-check against the older `plans/ipad-parity/13-*.md`.** The two View ▸ Windows diagnostics panes were the real hole: theme 02 row 85 covers the grid's *Find Possible Source Effects* entry point, but nothing covered the **Search Effects** panel (rows 86, 87), whose regex + Select-All is the only way to bulk-select every effect carrying a given setting. The other four are diagnostics plumbing that no scorecard owned: exception description (88), `ShowGUID` (89), log rotation budget (90), and the iPad-only Tools ▸ Edit Layout entry (91). Row 90 is the cheapest real improvement in this theme — one constant.

- **Structural note on the command palette (row 84).** Desktop's palette is derived — it walks `GetMenuBar()`, so it cannot drift. iPad's is declared — `CommandPaletteRegistry` is 45 hand-written entries that must be updated whenever `XLightsCommands.swift` changes. The same hand-maintenance problem appears in row 61 (`KeyBindingsSheet` mirrors `XLightsCommands.swift` by hand). Both would be worth generating from a single table on the iPad side; a command list, a palette, and a keybindings cheat sheet are three views of one dataset.
